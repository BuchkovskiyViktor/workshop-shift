.B.A.D.Workshop v6 — SERVER UPDATE
=================================

Это обновление существующей серверной v5. Оно рассчитано на сохранение текущей базы Supabase, проектов, сотрудников, смен, выплат и расходов.

ВАЖНО: ПЕРЕД УСТАНОВКОЙ
-----------------------
1. Не удаляйте текущий Supabase Project.
2. Не создавайте новую базу и не запускайте старые черновые схемы v4/v5.
3. Сначала выполните supabase-migration-v6.sql в существующем проекте Supabase.
4. Только после успешного SQL обновляйте файлы GitHub Pages.
5. В архиве config.js содержит Project URL и Publishable key текущего проекта. Publishable key предназначен для браузерного приложения; секретного service_role ключа в архиве быть не должно.

ЧТО НОВОГО В v6
----------------
1. Руководитель может изменить название, описание и статус проекта.
2. Правка участка смены включает проект, вид работы, тип, время начала/окончания, комментарий сотрудника, ответ руководителя и ставки.
3. При изменении типа смены ручная ставка сбрасывается к тарифу нового типа, если руководитель не вводит новую цену вручную. Это исправляет дефект v5, когда стоимость не пересчитывалась из-за старого override.
4. При подтверждении смены руководитель может оставить автоматический расчёт или указать собственную итоговую сумму. Смену можно вернуть на исправление или отклонить с обязательной причиной.
5. Сотрудник видит причину возврата/отклонения; возвращённую смену можно отправить на повторную проверку.
6. Руководитель может редактировать все основные поля смены, участков, расходов, выплат, доходов и прямых затрат проектов.
7. В карточке сотрудника доступны индивидуальные переключатели функций: «Дела», выбор типа смены, расходы, комментарии, приватные заметки и смена участка. Ограничения проверяются не только в интерфейсе, но и триггерами базы.
8. Руководитель может редактировать, отключать, упорядочивать и добавлять варианты в выпадающие списки. Поддерживаются дополнительные типы смен с отдельными ставками для каждого сотрудника и проектные ставки переработки.
9. В «Делах» есть пояснение, отдельная ветка комментариев, приоритет, порядок, дата/время напоминания, локальное уведомление при открытом приложении и переключатель Telegram. Если приложение закрыто, для гарантированной доставки напоминания требуется настроенный Telegram.
10. Добавлена очередь офлайн-действий и локальный снимок данных. Начало/окончание смены, смена участка, расходы и дела могут сохраниться на телефоне при потере соединения и отправиться после восстановления сети. Сначала приложение нужно хотя бы один раз открыть онлайн на этом устройстве.
11. PWA Service Worker обновлён до v6 и пытается кэшировать библиотеку Supabase, чтобы ранее загруженное приложение могло открыться офлайн.
12. Добавлена серверная Edge Function для Telegram: уведомления о начале/окончании смен и отправка напоминаний по задачам.

ШАГ 1 — РЕЗЕРВНАЯ КОПИЯ
-----------------------
В Supabase откройте свой проект и убедитесь, что это тот же проект, где уже есть текущие данные. Перед изменением схемы сохраните резервную копию доступным для вашего тарифа способом. Не удаляйте и не пересоздавайте проект.

ШАГ 2 — МИГРАЦИЯ БАЗЫ
---------------------
1. Supabase → SQL Editor → New query.
2. Откройте файл supabase-migration-v6.sql.
3. Скопируйте всё содержимое и вставьте в SQL Editor.
4. Нажмите Run.
5. Дождитесь успешного завершения. В Table Editor должны появиться новые таблицы app_options, shift_type_rates и todo_comments.

Если SQL Editor покажет ошибку — остановитесь и пришлите текст ошибки. Не удаляйте таблицы и не запускайте случайные SQL-команды.

ШАГ 3 — ОБНОВИТЕ GITHUB PAGES
-----------------------------
1. Откройте репозиторий workshop-shift на GitHub.
2. Загрузите файлы v6 в корень репозитория с заменой старых файлов: index.html, app.js, config.js, service-worker.js, manifest.webmanifest, icon-192.png, icon-512.png.
3. Можно также загрузить README.txt, CHANGELOG.txt, SQL и папку supabase — они не мешают GitHub Pages.
4. Сделайте Commit changes и дождитесь обновления GitHub Pages.
5. На телефоне полностью закройте установленную PWA и откройте снова. Если старая версия осталась, откройте сайт в браузере и обновите страницу; иногда требуется удалить старую иконку с экрана и добавить её снова после обновления сайта.

Не заменяйте config.js на шаблон с пустыми значениями: он должен содержать текущие Project URL и Publishable key.

ШАГ 4 — ПЕРВАЯ ПРОВЕРКА v6
--------------------------
1. Войдите руководителем и проверьте, что проекты и сотрудники на месте.
2. Измените название тестового проекта и верните прежнее название.
3. Создайте тестовую смену на другом телефоне.
4. В проверке смены измените тип участка: расчётная ставка должна измениться согласно тарифу нового типа. Проверьте ручную ставку и пустое поле итоговой суммы.
5. Подтвердите тестовую смену с автоматическим расчётом, затем отдельную тестовую смену с вручную указанной суммой.
6. Проверьте «Вернуть на исправление» и повторную отправку.
7. Создайте дело с пояснением, комментарием, приоритетом и напоминанием.
8. На тестовом сотруднике выключите «Дела» или выбор типа смены и проверьте интерфейс и сохранение.
9. Откройте приложение онлайн, затем включите авиарежим и попробуйте начать/завершить тестовую смену. После восстановления интернета проверьте, что очередь отправилась. Не используйте реальную оплачиваемую смену для первого офлайн-теста.

ОФЛАЙН — ВАЖНО
--------------
- Офлайн-режим работает после хотя бы одного успешного онлайн-входа и загрузки данных на этом устройстве.
- Смена, участки, расходы и дела поддерживают локальную очередь. Большая часть административных правок руководителя пока требует интернета.
- Если долго работать офлайн на нескольких устройствах, возможны конфликты. После восстановления связи дождитесь сообщения о синхронизации и проверьте смену на втором телефоне.
- Не очищайте данные браузера и не удаляйте приложение, пока есть несинхронизированные действия.

TELEGRAM — ДОПОЛНИТЕЛЬНАЯ НАСТРОЙКА
----------------------------------
Telegram не начнёт отправлять сообщения только от загрузки файлов. Нужно один раз развернуть Edge Function и включить расписание. Пока это не сделано, смены и напоминания продолжают работать в приложении, а ошибки Telegram не должны блокировать работу.

1. Создайте бота через @BotFather и сохраните токен приватно.
2. Для уведомлений укажите личный чат руководителя или закрытую группу только для руководителей — тогда сотрудникам не будут приходить Telegram-уведомления.
3. Узнайте chat_id: напишите боту /start, затем откройте getUpdates для своего бота и найдите message.chat.id. Не публикуйте URL с токеном.
4. Разверните папку supabase/functions/bad-workshop-telegram через Supabase CLI. Файл supabase/config.toml задаёт verify_jwt=false; функция сама проверяет сессию пользователя для событий смен, а cron-вызов защищён отдельным CRON_SECRET.
5. В Supabase → Edge Functions → Secrets добавьте TELEGRAM_BOT_TOKEN, TELEGRAM_CHAT_ID и CRON_SECRET. Используйте длинный случайный CRON_SECRET и то же значение в SQL-шаблоне расписания.
6. В файле telegram-cron-template.sql замените PROJECT_REF на идентификатор проекта и CRON_SECRET_VALUE на то же значение, которое установили в секрете CRON_SECRET. Выполните SQL в SQL Editor. Он включает вызов проверки напоминаний раз в минуту.
7. Проверьте тестовое начало/окончание смены и напоминание на время через 2–3 минуты в будущем.

Пример команд для компьютера, если Supabase CLI уже установлен:
  supabase login
  supabase link --project-ref YOUR_PROJECT_REF
  supabase functions deploy bad-workshop-telegram --no-verify-jwt

Не вставляйте TELEGRAM_BOT_TOKEN, service_role или другие секреты в config.js, app.js, GitHub Pages или чат.

ФАЙЛЫ
-----
- index.html / app.js — PWA.
- config.js — URL и публичный Publishable key текущего проекта.
- service-worker.js — кэш оболочки и попытка кэшировать библиотеку Supabase.
- supabase-migration-v6.sql — обязательная миграция существующей базы.
- supabase/functions/bad-workshop-telegram/index.ts — серверные Telegram-уведомления и обработчик напоминаний.
- supabase/config.toml — настройки Edge Function.
- telegram-cron-template.sql — шаблон расписания Telegram-напоминаний.

Ограничение: исходный архив не содержит экспорт фактической схемы Supabase, поэтому миграция составлена по таблицам и полям, которые использует работающая v5. До реального выполнения в вашем Supabase нельзя подтвердить совместимость со всеми особенностями текущей базы. Если миграция выдаст ошибку, не продолжайте замену приложения до её исправления.
